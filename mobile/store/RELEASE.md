# Ziipa mobile release checklist

Prepared 2026-08-31. This is a release plan, not an assertion of store approval. Do not submit a development server or placeholder policies to review.

## What is ready in the repository

Native iOS/Android app source, original in-app branding, creator workflow, shared API integration, encrypted session storage, reporting/blocking/deletion, a native Android project generated by Expo, EAS development/preview/production profiles, signed-binary build commands, draft store text, and automated checks. Both platform JavaScript/Hermes bundles can be exported on Windows. This machine has no Android SDK/emulator or Xcode; no native app binary or real-device test has been completed.

## Required before store submission

- [ ] Owner-controlled Expo organization/project, Apple Developer Program/App Store Connect account, and Google Play Console account; accept agreements and finish identity/organization verification yourself.
- [ ] Confirm `ZIIPA_APP_ID` (provisional `com.ziipa.app`) and reserve matching identifiers. Do not change the Android application ID after first publication. Preview uses `.preview`.
- [ ] Deploy and secure the FastAPI API, database, Redis, and persistent media storage behind HTTPS. Configure origins/cookies, secrets, migrations, backups/restore, quotas, rate limits, monitoring, retention and recovery. Add email verification and password recovery.
- [ ] Verify the final API URL on physical iOS and Android devices. Localhost, the emulator host address, and an unauthenticated development tunnel are not production services.
- [ ] Publish reviewed privacy, terms, community policy, support, and account-deletion pages. The local `/account-deletion` page is implemented but must be deployed against the production API. Final policies need operator identity, jurisdiction/retention, backup deletion, and appeals details. Existing member consent/age handling also needs review.
- [ ] Staff moderation, define response/escalation/appeal workflows and child-safety standards, and implement baseline objectionable-content filtering or prepublication review before enabling public UGC. Current personal filters + report/removal endpoints alone are not a complete platform safety operation.
- [ ] Decide and complete store age/content questionnaires based on actual content. The initial native registration asks users to confirm 18+, but self-declaration alone is not a comprehensive age-assurance system.
- [ ] Disable sample catalogue and unconnected concept categories in production. Review all copy to remove development policy language. Include no nonworking financial/live/AI promises or disabled placeholder screens in the store release.
- [ ] Review/approve launcher artwork and real device screenshots. The original in-app logo is unchanged; the launcher is a generated brand treatment and needs owner approval. Do not present concept images as captured app screenshots.
- [ ] Complete App Privacy / Google Play Data safety accurately using `DATA-DISCLOSURE.md`, including server logging and all selected production vendors. Recheck native privacy manifests and merged permissions on signed builds.
- [ ] Run the physical-device QA checklist below. Confirm accessibility, performance and account deletion on the same build that will go to review.
- [ ] Prepare a valid reviewer account and review notes. The reviewer must reach the live backend and all submitted features without contacting the developer to unlock them.
- [ ] Complete TestFlight and Google Play internal/closed testing as required by your account type, then address the results.

## Build and submit after the checklist is satisfied

Install the current EAS CLI and sign into your own account interactively. Do not paste credentials into chat or the repository. The CLI can manage signing in the owner account; use its secure credential workflow.

```powershell
npx.cmd eas-cli@latest login
npx.cmd eas-cli@latest init
```

Because `app.config.ts` is dynamic, put the resulting project ID in `EXPO_EAS_PROJECT_ID` and organization/account name in `EXPO_OWNER`. Create the public configuration values listed in `.env.example` in the relevant EAS environment. Configure `ZIIPA_APP_ID` and `EXPO_PUBLIC_SUPPORT_EMAIL` too. `EXPO_PUBLIC_*` values are not secrets. Keep Apple/Google signing and submission credentials in EAS/your CI secret manager, never in those variables.

```powershell
# First installable internal builds (requires HTTPS staging API):
npx.cmd eas-cli@latest build --platform android --profile preview
npx.cmd eas-cli@latest build --platform ios --profile preview

# Production checks must pass before signed store builds:
npm.cmd run release:check
npx.cmd eas-cli@latest build --platform all --profile production

# Only after review of the actual built artifacts:
npx.cmd eas-cli@latest submit --platform ios --profile production
npx.cmd eas-cli@latest submit --platform android --profile production
```

`eas init/build/submit` are intentionally **not executed** as part of this local implementation. Build uploads source to Expo and may consume paid build capacity; submission uploads binaries to Apple/Google. Confirm the owner account, configuration, and artifact before doing these steps.

The production profile produces an Android **AAB** and signed iOS **IPA** through EAS. Android submission targets the internal track with draft release status; iOS upload goes to App Store Connect, where TestFlight and release review remain separate actions. Configure App Store Connect `ascAppId`, Apple team, and Play service-account/submission settings in the owner-controlled workflow. Google may require the first upload through Play Console before API submissions.

`scripts/check-release.cjs` runs as an EAS production pre-install hook. It deliberately blocks missing public URLs, missing app/project identity, enabled demos, and an incomplete release review. Set `ZIIPA_RELEASE_REVIEWED=true` only after completing the actual checklist; the variable is an acknowledgment, not an automated compliance verdict. CLI local `release:check` reads the current shell environment; set the same values you will use in EAS.

## Physical-device QA

Test at least one supported iPhone and Android device, small and large display sizes, and current/minimum supported OS versions. Use the signed preview binary, then repeat critical flows on the store binary:

1. Cold launch, splash/icon, onboarding, registration/terms, existing portal login, bad password, expiry, logout, sign-in as another account and process restoration. No previous account’s screens/data should survive logout.
2. Camera and microphone permission allowed/denied, photo/video recording, and file-picker cancellation; MP4/MOV/WebM, common image and audio uploads, 100 MB rejection, low storage, slow/interrupted network and retry. No duplicate posts on retry.
3. Creator workflow persistence for trim, captions, overlays, soundtrack settings and selected networks; connection-required and unsupported-media delivery states; disconnect/revoke behavior. Real provider posting needs separate sandbox and reviewed-app test plans per provider.
3. Draft privacy with two accounts; publish, edit and retract; media range playback; landscape/fullscreen where allowed, mute, pause on navigation/background, trimming/captions and unsupported codecs.
4. Comments, bookmarks/likes, feed saving/filtering/sharing, block/unblock, word filtering, reporting a post/comment, moderator review/removal, and preventing removed posts from being republished.
5. Deletion with wrong password, confirmation cancellation, successful deletion, both devices losing access, failed-file cleanup retry, and the outside-app deletion page.
6. VoiceOver/TalkBack, text scaling, dark appearance, keyboard visibility, safe areas, contrast, touch targets and Android back navigation. Measure memory and playback startup rather than assuming desktop bundle checks establish performance.

No device/emulator, visual or end-to-end UI QA is claimed by the repository’s TypeScript, unit, API, or bundle checks.

## Official references checked

- [Expo SDK 57 reference](https://docs.expo.dev/versions/v57.0.0/) — native version compatibility.
- [EAS Build](https://docs.expo.dev/build/introduction/) and [EAS Submit](https://docs.expo.dev/submit/introduction/) — signed builds and submission workflows.
- [Apple App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) — functioning backend/review access, UGC safety, account deletion, privacy and payment rules.
- [Google Play account deletion](https://support.google.com/googleplay/android-developer/answer/13327111) — in-app and outside-app deletion paths and disclosure.

Recheck store requirements at submission time. The new wallet implements testnet minting, creator tokens, transfers and tips; no mainnet or production subscription/checkout path is enabled. Complete [the Web3 checklist](../../WEB3.md) and current policy/billing review before public distribution. The release check also requires a configured WalletConnect project/application origin and `ZIIPA_WEB3_REVIEWED=true`. This is an acknowledgment, not certification.

Wallet device QA must cover QR/native URI pairing, cold start/reconnect, user rejection, account/network changes, app backgrounding and return from wallet, ownership signatures, actual mint/transfer/tip approval, interrupted API submission with pending-hash recovery, insufficient gas, dropped/replaced transactions, failed receipts, and wallet unlink/account deletion. Verify public IPFS availability independently and never test with real funds or reused development keys.
