# Ziipa Live audience CRM design

The Audience tab in each creator’s Live studio should show three things: audience activity by source, contacts who chose to connect with that creator, and that broadcast’s engagement timeline. Ziipa can ship the first version using its own audience data and offer source-specific live views as integrations become available. A contact may span networks only where Ziipa has both viewer-authorized proof of the link and permission to use the source data for that purpose.

## Fit with the existing app

- `backend/profile_follows.py` owns native follow relationships and applies active-account, private-profile and block rules. Keep it authoritative. Following a profile grants the access the follow feature describes. Enrollment in a creator’s contact list or communications requires its own action.
- `backend/live_api.py` owns Livepeer streams and the Twitch destination lifecycle. `backend/live_webhooks.py` binds signed recording notifications to the owning stream. Add audience adapters beside that code and reuse the verified inbox and broadcast owner. The production capability evidence documented in `deploy/LIVE-TRANSITION.md` concerns broadcast and recording only.
- `backend/social_publishing.py` stores creator publishing grants per owner and provider. Keep audience ingestion, viewer claims and publishing as distinct grants. A creator’s publishing connection cannot prove a viewer’s identity or authorize audience reuse.
- Extend the authenticated export and deletion paths in `backend/account_services.py` and `backend/mobile_api.py` for the viewer’s data and creator-owned audience workspace. Keep the public Live Feed and profile collection APIs clear of private contact data.

## Identity and consent

**Scope each graph to one `owner_id`.** A viewer joining two creators has two contact IDs. Staff with approved workspace access see only the portion allowed by their role. Keep provider identifiers opaque, case-sensitive and keyed by their documented scope. Never use screen names, profile photos, IP addresses, device fingerprints, email similarity, chat style or coincident activity as identity evidence. A renamed handle changes the display metadata of an existing subject. A reused handle gives no relationship to its previous owner.

Use a star per contact rather than a global person graph. For example, the same verified Ziipa viewer can claim `twitch / user / 5738` and a second permitted subject for creator 42. Each subject remains independently revocable. A different creator never sees those contact IDs, links or proof records. A first-party campaign link can carry a signed campaign reference that the viewer sees when joining. It identifies the referral source for that signup while leaving any off-platform account unknown.

1. The authenticated viewer chooses **Join this creator’s audience** from the live event or creator profile. Explain the data the creator will see, the purpose, access duration, and the viewer’s controls. Store creator-specific consent against the current notice version. Keep email or SMS authorization separately opt-in by channel and purpose. The beta can omit contact details from the creator UI and leave messaging out entirely.
2. A viewer starts **Link an account** from their own audience settings. Issue a short-lived, single-use OAuth state bound to the viewer session, owner, provider app and requested purpose. Exchange the callback code server side, use PKCE where supported and validate the provider’s issuer, client and subject according to the provider flow. For OIDC, also validate the nonce and token signature. Obtain the stable user or channel identity through the authorized API and show the verified alias before confirmation. A verified in-platform challenge can be added only if its provider permits that use and its reply proves the same stable ID as the event feed.
3. The confirmation transaction consumes the intent once, rechecks viewer consent and provider capability, and creates a new evidence record and active membership. A conflict with a different viewer’s active claim stays unlinked until resolved through proof of control. Creator UI never offers a manual merge by handle. Delete short-lived proof tokens once verified unless the provider flow requires keeping an encrypted revocable grant. The connection screen shows purpose, expiry and disconnect controls.
4. Claims apply to events from the opt-in time forward by default. A separately disclosed historical import can be designed later for a bounded period where the source permits it. A revoked claim does not silently regain old event history when renewed.

Audience enrollment is independent of authentication. First-party session analytics can use a random token scoped to this broadcast where permitted, rotated after it ends. Public counts can include unauthenticated views without creating contacts. An anonymous provider gift contributes only a permitted source-specific anonymous count and has no stable identity node.

## Relational contract

Use PostgreSQL in the current API and worker stack. The table names below define the audience projection beside the control-plane SQL. `owner_id` uses the same integer type as `users.id`. Graph and event detail IDs are UUIDs. Every child reference that crosses a private table includes `owner_id`, and each target has `PRIMARY KEY (owner_id, id)` or an equivalent composite unique key. App routes and worker jobs derive owner scope server side. Use PostgreSQL row security for audience reads as defense in depth, with a non-owner API role, a transaction-bound owner context and tests for pooled connections and privileged worker boundaries.

The creator read surface can use `GET /api/live/broadcasts/{id}/audience` for one broadcast and `GET /api/live/audience/contacts` for their workspace. Use `private, no-store` on the API and exclude these routes from public feed caches. Keep event readers constrained to approved capabilities rather than exposing general-purpose graph traversal.

### Event ingress and attribution

The platform adapter verifies the provider signature and freshness before trusting a webhook or authenticates an approved API transport. Map the verified subscription or authenticated feed and its channel to a server-owned grant. Preserve both stable message IDs and provider business event IDs when supplied. Transfer only allowed data from the verified inbox and acknowledge deliveries after commit. Prefer a specific provider event for each metric; if chat and subscription feeds overlap, use documented shared business IDs or pick one source for the counter. Never collapse two gifts by name and timestamp. Keep a moderation deletion or message retraction as a removal command for any stored copy within the relevant permission and TTL. Twitch EventSub version, message ID, revocation and callback verification each have explicit handlers. [Twitch EventSub webhooks](https://dev.twitch.tv/docs/eventsub/handling-webhook-events/)

Use the core CloudEvents `source` plus UUID `id` for delivery deduplication. Normalize only explicit claims from a provider. Example internal event `com.ziipa.live.audience.activity.recorded.v1` has schema version, opaque `activity_id` and, if known, `broadcast_id`, `manifest_revision`, `generation`, and `destination_id`. Protect data by reference. Keep actor identifiers, handles, chat text, monetary details and token material out of the immutable outbox. Receivers obtain detail through a scoped lookup that can fail closed on withdrawal, expiration or deletion. An external notification cannot enrich from the private graph.

Bind external activity by verified stream, channel and occurrence identifier where known. The same channel can host sequential events and overlapping callbacks. An event without a trustworthy occurrence mapping stays source-specific and unattributed, even if an event is currently scheduled on that channel. Record both source time and receipt time. Downstream chronology or a late recording marker never changes broadcast lifecycle state. Expose data freshness and incomplete intervals to the creator.

### Merge, unlink and rollups

Serialize graph changes and revocations with an owner-scoped row lock, stable UUID ordering for affected rows, and expected epoch. Two provider claims confirmed against the same opted-in Ziipa viewer extend one contact. If contacts need a merge after a supported account consolidation, require proof for each surviving membership and consent for the destination owner. Move the current edges, close obsolete ones and record a minimal private audit receipt in one transaction. When either account cannot be proved, keep its node separate. A later split closes specific affected edges, removes contact attachment and permits a fresh link only with valid consent and evidence. Raw event ownership never moves between creators and historical event authors are never overwritten.

Append facts once and build projections by joining eligible facts to current authorization. For an event at `occurred_at`, require an eligible source permission, matching owner, purpose and subject, a membership interval covering the event, and a corresponding consent and proof still valid now. A late event predating a new claim stays unlinked. For a revoked grant or claim, remove affected activity from contact totals immediately. Retain source-only facts only where separately permitted. A new claim begins at its own `valid_from`.

The contact summary query starts from an `eligible_crm_activity` view that protects owner scope, expiry, destination validity when required, moderation removals and active source permission for `crm_activity`. A second `active_crm_membership` view applies owner scope and checks contact, edge, subject, grant and proof eligibility. Both views must apply the actual current policy at read time. The join below is sufficient once those two guarded views exist.

```sql
SELECT link.contact_id, count(DISTINCT activity.id) AS observed_interactions
FROM eligible_crm_activity AS activity
JOIN audience_activity_actor AS actor
  ON (actor.owner_id, actor.activity_id) = (activity.owner_id, activity.id)
JOIN active_crm_membership AS link
  ON (link.owner_id, link.subject_id) = (actor.owner_id, actor.subject_id)
 AND activity.occurred_at >= link.valid_from
WHERE activity.owner_id = :authorized_owner_id
  AND activity.broadcast_id = :authorized_broadcast_id
  AND actor.role IN ('commenter', 'gifter', 'reactor')
GROUP BY link.contact_id;
```

Filter permitted actor roles by metric and count each fact once per contact. The distinct activity count in this example handles several approved subject edges attached to one activity. Source totals remain separate and report their own units.

For beta, query the bounded event tables directly for private timelines and contact summaries. Once rollups are needed, use a transactionally incremented `identity_epoch` and a `com.ziipa.live.audience.projection.invalidated.v1` outbox event on consent, evidence, deletion or source permission changes. Rebuild affected buckets from currently eligible facts with deduplicated event keys, then publish only under the epoch read by the rebuild. Read paths require a matching epoch and recheck `expires_at` so a missed timer cannot leak stale permissions. If a result is stale, return source-only data or a recomputing state. Scheduled expiry and projection rebuilds should be idempotent.

Example acceptance fixture with permission to join two sources: viewer A joins creator 42 and claims both subjects. One permitted event from each subject during the claims gives two observed interactions and one linked contact. Replaying either delivery keeps those counts. If A withdraws the second claim, the contact shows one eligible interaction. The second source can still show an unlinked permitted interaction. Showing one contact never implies one total viewer across those networks.

An engagement event and a payment settlement are separate records. The event may carry a provider-supplied quantity and unit such as `gifts`, `bits`, or `currency_micros` with original currency. Leave absent amounts unknown and preserve integer units. A gifter and recipients are different roles. Never infer a dollar amount from a subscription tier or count, assume the purchase amount is the creator’s take, convert between tokens and cash for a unified total, or book an event from chat as recognized revenue.

If statements are available under an authorized finance scope, import them into a separate restricted settlement ledger. Key by owner, provider, merchant/account and stable statement/line ID. Carry period, statement category, reported amount, currency/unit, actual fees, refunds and net where supplied. Store append-only corrections/reversals and handle late documents. Reconcile confirmed statement lines to an activity only when there is a provider-supported reference. Keep unallocated amounts visible as such. A 4.99 USD Super Chat display is a gross viewer amount in its source view. Show creator payout only from a corresponding verified statement, with provider and interval identified. This beta can show permitted provider receipts without making a tax or payout claim.

## Privacy and launch sequence

1. **First-party beta.** Add a private **Audience** view to Live & recordings, showing Ziipa activity where permitted and a **View contacts** link beside source cards. Viewer joins and opts out in their own account. Use the existing PostgreSQL and bounded worker. Add previews with synthetic events and no real notifications. Creator controls specify the one workspace and the data shared. Hide unavailable provider capabilities with a short status and a link to connection settings. Keep ranking, outreach and automatic triggers off.
2. **Approved source adapters.** Add Twitch or another approved provider one at a time. Verify scope, destination mapping, duration and purpose in real provider test events. Use transient source-labelled engagement display after review. Default proposed maximum for transient raw envelope detail is 24 hours, shortened where the provider or intended purpose requires it. Keep durable inbox dedup keys only as long as allowed and needed for the provider’s authenticated replay horizon. Other retention is purpose-specific, documented on the grant and enforced in live queries, the purge job and backups.
3. **Verified joins and optional finance.** Enable only approved provider/purpose combinations after viewer claim, disconnection and cleanup work in an end-to-end test. In Audience, distinguish **Linked contacts**, **Source activity** and **Provider payout reports** using actual permitted data. Subsequent automated contact or reward delivery requires separate approval and communication consent.

In beta, a viewer can see linked sources and participating creators, withdraw contact use, export their data, or request deletion from account settings. On revocation, block the relevant jobs and private reads immediately, close the edge or grant, remove restricted payloads and actor relationships, and rebuild projections and cached exports. Invalidate download links and recheck scope when exported data is fetched. Avoid storing raw external chat by default. Keep any short-lived retention in encrypted restricted storage. Logs, telemetry, action notices and public feeds receive no private identity data. Apply provider-required removal windows and retain any lawful finance records separately under appropriate oversight. Backup restores must apply outstanding removals before serving requests. When no retention permission continues, delete keys, maps, evidence, raw payloads and projections or irreversibly aggregate only where permitted. Replay rejection relies on the verified subscription state and source freshness, not indefinite retention of a person’s ID.

### Acceptance checks

- A viewer using the same nickname on two providers remains two unmatched subjects until verified claims exist. A duplicate callback, expired OAuth state, incorrect app scope or competing claim cannot attach an account.
- Claims to distinct Ziipa creators create distinct contact IDs. A creator account, staff route, worker and event export cannot read another owner’s contacts or audience permissions. Public feed playback and native follows still work without CRM enrollment.
- A provider declares an anonymous gift. Its allowed native quantity increases once and creates zero identity edges. A gifter and recipient remain separate. A retraction clears protected payload and dependent projections.
- An event arrives after reconnect for an older destination epoch. It attaches to that original occurrence only when provider proof exists and never updates the current output state. A conflicting duplicate is quarantined.
- With deletion, opt-out, expired scope or a provider disconnect, private contact totals re-evaluate immediately. Delayed producer retries and a restarted projection worker do not restore revoked edges. Rejoining creates a new interval.
- A source grant supports read-only display. Its records cannot enter identity resolution, cross-platform metrics, an LLM task, a trigger or payout ledger. Expired provider data disappears even if cleanup is delayed.
- Refund and duplicate settlement tests leave confirmed provider totals correct. No normalized engagement event is recorded as revenue by default.
